01The Problem

It started as nostalgia — rebuild the platformer I grew up on, just for the fun of seeing it run again. That's where it stayed a toy: draw a canvas, add gravity, let a rectangle jump over other rectangles. It stopped being a toy the moment the plan became to actually ship it — post a public link, put it in front of strangers on LinkedIn and an AWS community. That's where three problems that don't matter for a private prototype suddenly do:

  • The obvious character choice is a trademark landmine. The natural instinct for a retro platformer is the cap, the mustache, the red overalls. Fine for something only I ever open. Not fine for a public, sharable link — Nintendo enforces the Mario IP aggressively, and a lookalike clone with your name on it is exactly the kind of thing that gets a takedown notice.
  • Hand-typed level coordinates don't scale. One level with a dozen platforms, typed as literal tile numbers, is manageable by eye. Five levels — each needing 4 to 10 gaps and several bonus platforms not to overlap anything — is not. Every manually computed offset is a chance to place two things where they shouldn't touch.
  • "I played it and it worked" isn't proof. A human playtester — including me — samples the first 20 seconds of a level far more thoroughly than the last 20. That's exactly where a level-breaking bug hides, and exactly where mine did.

02The Approach

Three decisions shaped everything that followed:

  • Original IP, not a clone. Its own name (Pixel Plumber), its own logo mark, its own mascot design — close enough to the genre to read instantly as "platformer," far enough from Mario's specific silhouette to be safe to post under my own name.
  • Levels as data, not hand-placed pixels. Each level is a short list of {len, gap} tile-run segments, expanded into real platform coordinates by one function. Bonus platforms are described as "put one on segment 4," not as raw x/y numbers — the placement math happens once, in one place, instead of five times by hand.
  • A bot that never gets tired. Before any level shipped, a small script played it end-to-end: hold right, jump when a pit or enemy comes up, record whether it reaches the flag. It doesn't get bored halfway through the way a human tester does — which is exactly how it caught a level that was, at one point, mathematically unbeatable.

03How I Built It

Step 1 — Engine core

No framework, no build step — one canvas, one requestAnimationFrame loop, and a handful of physics constants tuned by feel:

game.js 
const GRAVITY = 0.6, FRICTION = 0.8;
const MOVE_SPEED = 4.2, JUMP_FORCE = -13.5, TILE = 40;

function loop() {
  update();
  draw();
  requestAnimationFrame(loop);
}

Step 2 — Collision, and the bug hiding in the obvious version

Standard AABB collision: move on one axis, push the player back out of anything it now overlaps. The first version resolved horizontal movement, then vertical. That ordering has a quiet failure mode — covered in full in Lessons — that silently broke coin pickups near platform edges.

Step 3 — Levels as declarative data

Instead of typing absolute tile coordinates for every platform, each level is a chain of ground lengths and gap widths. One function turns that into real segments — so a gap is always exactly as wide as intended, never off by an arithmetic slip:

game.js — buildGround() 
function buildGround(pattern) {
  const segments = [];
  let cursor = 0;
  for (const seg of pattern) {
    segments.push([cursor, cursor + seg.len]);
    cursor += seg.len + seg.gap;
  }
  return segments;
}

// 8 tiles of ground, a 2-tile pit, 6 tiles of ground, a 2-tile pit...

  { len: 8, gap: 2 }, { len: 6, gap: 2 }, { len: 8, gap: 2 },

Step 4 — Bonus platforms that place themselves

Floating coin platforms used to be hand-placed by tile number. That's exactly where the worst bug in this project came from (see Lessons). The fix: describe a bonus platform as "somewhere safely inside segment 4," and let the engine center it with margin on both sides automatically:

game.js — auto-centered bonus platforms 
for (const segIdx of spec.bonusSegments || []) {
  const [s, e] = segments[segIdx];
  const segW = e - s;
  if (segW < 7) continue; // too narrow to fit one safely — skip it
  const w = Math.min(3, segW - 4);
  const x = s + Math.floor((segW - w) / 2);
  platforms.push({ x: x * TILE, y: 9 * TILE, w: w * TILE, h: TILE });
}

Step 5 — A bot that plays the level for me

Before any level shipped, a headless script held the right-arrow key and jumped proactively whenever a pit or enemy entered a lookahead window, logging deaths, coin pickups, and whether it ever reached the flag:

verification harness 
const lookX = player.x + 46;
const nearPit = level.pits.some(p => lookX > p.x - 6 && lookX < p.x + p.w + 6);
const nearEnemy = level.enemies.some(e =>
  e.alive && Math.abs(e.x - player.x) < 55 && Math.abs(e.y - player.y) < 70
);
keys.jump = player.onGround && (nearPit || nearEnemy);

Run against all five levels, it either reports WON at frame N or gets stuck — which is exactly how level 4 revealed itself as unbeatable before a single human ever hit play.

Step 6 — Original branding

Once the plan became "share this publicly," the mascot got a full redesign: teal overalls and an amber cap instead of red, goggles instead of a mustache, plus an original pixel-badge logo for the marquee — its own visual identity, not a Mario recolor.

Step 7 — Shipping it

The whole game — HTML, CSS, and JS — lives in one self-contained file, which made distribution trivial: no bundler, no assets to path-fix. It's deployed to Vercel for a stable, no-login-required public URL, and mirrored as a Claude Artifact for quick iteration and sharing.

05By the Numbers

  • 5 levels, each verified completable end-to-end by the automated bot before shipping
  • 504 tiles of combined level length (~20,160px) — roughly 6× the length of the original single-level prototype
  • 34 pits total across all five levels, none wider than 2 tiles (safely under the ~4-tile max jump distance)
  • 36 enemies total, patrol speed scaling from 1.6px/frame on level 1 to 2.4px/frame on level 5
  • 2 shipping-blocking bugs the bot caught that manual playtesting had missed

06Challenges & Lessons Learned

1. The axis-order collision bug

The original collision code resolved horizontal movement before vertical. If the player was moving sideways at the exact moment they should have landed on a platform's top, the horizontal check ran first, saw an overlap, and read it as hitting the platform's side — shoving the player backward instead of letting them land. It silently broke coin pickups near platform edges too, since the coin check happened after a landing that never correctly occurred.

Failure mode

Player lands on any platform while still holding a direction key → gets bounced back off it instead, sometimes losing all horizontal momentum mid-jump.

Fix

Resolve vertical collision before horizontal. By the time the horizontal pass runs, a successful landing has already snapped the player exactly onto the platform's surface — with no vertical overlap left for the side-check to misread.

2. The bonus platform that made a level unbeatable

Hand-placed bonus platforms used the same "extends to the floor" height as ground platforms. On one level, a bonus platform's collision box reached all the way down and overlapped the pit beside it — turning a floating coin bonus into a solid wall blocking the only path across. The automated bot died at the exact same tile 39 times in a row before I noticed the pattern wasn't bad luck.

Caught by

The verification bot — a human tester playing the first minute of five different levels is very unlikely to grind against the same wall 39 times and notice it's not chance.

Fix

Give bonus platforms a thin, fixed height instead of one that scales to the floor, and auto-center every one inside its segment with margin, rather than trusting hand-picked coordinates (Step 4, above).

3. Browser automation speaks a different dialect

Verifying the game in a remote browser-automation tool, none of the arrow-key presses registered — at all. The tool's synthetic key events set event.key but left event.code empty, and the input handler only ever checked event.code. A real keyboard sets both; this one didn't. The fix was reading both and normalizing:

game.js — normalized key handling 
function setKey(e, val) {
  if (e.code) keys[e.code] = val;
  if (e.key) keys[e.key] = val;
}

4. Choosing where to ship it

itch.io was the first stop — it's where platformers like this belong — but hit a Cloudflare bot-check loop and login friction that stalled the whole path. Vercel ended up the faster route to something genuinely public: no account needed to view it, no CAPTCHA in the way, one deploy command.

07Conclusion

None of this — the axis-order fix, the auto-centered platforms, the bot — is exotic engineering. It's a small platformer. But the failure modes it hit are the exact same ones that show up in far bigger systems: hand-authored data drifting out of sync with itself, a boundary condition that only breaks under a very specific combination of state, and the gap between "I tried it and it seemed fine" and "I can prove it works." A script that plays the whole game and reports pass or fail closed that gap here in minutes; it's worth having one before trusting anything you built by eye.

The other half of the lesson was less technical: the moment a hobby project has an audience, the easy defaults — a borrowed character, a hand-typed level, a spot-check playtest — stop being harmless shortcuts.
